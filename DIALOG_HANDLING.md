# Dialog handling reference

What unpredictable dialog/condition this automation watches for, where it's checked,
how long it keeps checking, and what happens when one appears. Generated by reading
the current `flows/`/`components/`/`assertions/` source directly (not from memory of
past sessions) -- if this drifts from the code, the code is correct and this should be
re-generated.

## The pattern this project uses everywhere

Nothing here is a one-shot "check once, assume it won't come back." Every dialog below
is **raced**: checked once per iteration of whichever wait loop(s) it can interrupt,
alongside the actual thing that loop is really waiting for. See `CLAUDE.md` for the
underlying convention (assertions = text + existence checks, locators = click targets,
components = click/type actions only, flows = the loop logic that ties them together).

Two outcomes, per dialog:
- **Non-fatal (click through)**: the matching action is clicked, the loop's `continue`s
  and keeps waiting for its real target screen. The dialog can reappear any number of
  times; nothing here counts "how many times."
- **Fatal (raise)**: the matching action is clicked (if there is one to click), then the
  flow raises immediately, ending the run. The caller's own cleanup (`Session.close()`
  in `orchestration/role_runner.py`) tears down the app/browser/WinAppDriver together.

**"Scope"/"till when"** below means: what bounds how long a loop keeps re-checking for
a given dialog. Three shapes exist in this codebase:
1. **Bounded by a fixed timeout** (e.g. `screen_timeout`, `discovery_timeout`) -- the
   loop gives up and raises once that elapses, dialog-handling time included.
2. **Deadline-extending** -- the loop's own deadline is pushed back by however long each
   interrupting dialog took to handle, so only genuine "nothing is happening" time counts
   against the real timeout. Used specifically for dialogs confirmed to legitimately
   repeat for a long, unpredictable time (e.g. a low-battery warning that only clears
   once a human actually plugs in a charger).
3. **Unbounded within the call** -- a handful of one-off checks (e.g. the browser's
   restore-pages dialog) that just fire once at a specific point, not inside a long poll
   loop at all.

## Target PC

### Browser sign-in page (`components/target/browser_sign_in_page.py`, driven by `flows/target/authentication/sign_in_flow.py`)

This is the OS-default browser, not the app window -- only reachable when a fresh
sign-in is actually needed (not every run; four "already signed in" shortcuts can skip
it entirely, see below).

| Dialog / condition | Heading / text | Where checked | Scope | Outcome |
|---|---|---|---|---|
| Chrome "Restore pages?" crash-recovery dialog | (Chrome's own UI, no app text) | 3 one-off checks: right after attaching the browser, and again at the password -> OTP transition (`sign_in_flow.py`) | Single check per call site, not a loop | Non-fatal -- `RestorePagesDialog.click_close()` dismisses it, confirmed to otherwise steal keyboard focus mid-typing |

### `SignInFlow` -- post-click-Sign-In, through to pairing-discovery (`flows/target/authentication/sign_in_flow.py`)

Four "already signed in" shortcuts (Welcome-back screen, pairing-discovery already
showing, trust-network already showing, pairing-code-entry already showing) can skip
straight past some or all of the browser/OTP sequence above -- confirmed live, the app
can have a valid cached session even when the plain "Welcome to Dell" screen shows.

| Dialog / condition | Heading / text | Where checked | Scope | Outcome |
|---|---|---|---|---|
| "Add a desktop shortcut before you go" | same | Raced in essentially every wait loop in this file (confirmed: can appear at ANY point between launch and pairing-discovery, no single confirmed phase) | Whichever loop's own timeout | Non-fatal -- clicks "Create shortcut" |
| "This PC isn't connected to a network." | same | `wait_for_source_pc()`, `_wait_for_trust_network_then_pairing_discovery()` | Plain `continue`, no deadline extension here | Non-fatal -- `NetworkDisconnectedDialog.click_check_again()` (waits 30s first) |
| "Plug into AC power" | same | Same two loops above | Same two loops; **see below -- this one needed more than click-and-continue** | Non-fatal, but see "Plug into AC power" special case below |
| "Set both of your PCs to the same supported region" | same (button: "Close") | Same two loops above | Plain `continue` until the raise | **Fatal** -- clicks Close, raises `SignInError` |
| "We couldn't sign you in" | same | Raced for the entire remaining wait after an earlier transition screen looked like success (`_LateSignInFailure`) -- not just a short fixed window, see `_wait_for_auth_outcome`/`_run_fresh_auth_with_retry` | Remaining step budget | Downgrades to a retry of the whole browser sign-in sequence, up to `MAX_AUTH_RETRIES` |

**"Plug into AC power" -- the special case (fixed 2026-10-14):** clicking its only
button, "Cancel transfer", does **not** cancel anything -- confirmed via three live
screenshots, it bounces all the way back to the "Welcome back" home screen, which needs
its own "Get started" button clicked again to re-enter. Re-entering replays the same
checking-your-PC/trust-network sequence from scratch, re-showing the identical dialog
if the battery is still low -- a real cycle that continues until the charger is
actually plugged in.
- `_wait_for_trust_network_then_pairing_discovery()`: click Cancel transfer -> click
  Get started (`_recover_from_plug_into_ac_power_reset()`) -> `continue` -- safe here
  because this loop's own success conditions naturally pick up once the app cycles back
  around.
- `wait_for_source_pc()`: click Cancel transfer -> click Get started -> **re-runs**
  `_wait_for_trust_network_then_pairing_discovery()` before resuming the search. A plain
  `continue` here would falsely declare "Source found" the instant the screen resets,
  since this loop's own exit condition is "pairing-discovery screen not showing."
- Confirmed scope: this reset only happens **before pairing** (Source isn't found/
  involved yet) -- not applied to `pairing_flow.py`/`transfer_flow.py`.

## Source PC

Both flows below share two plain functions in `flows/source/common_dialogs.py`
(`check_other_pc_disconnected`, `check_battery_critically_low`) plus two more added
later the same way (`check_welcome_screen`, `raise_if_regional_settings_not_supported`)
-- extracted specifically so a new shared dialog only needs editing in one file, not
both flows by hand (a lesson learned the hard way: the other-PC-disconnected fatal/
non-fatal fix originally had to be hand-applied in two places).

### `SourcePairingFlow` (`flows/source/pairing_flow.py`)

Covers: Welcome screen -> "Let's get started" -> trust-network dialog (if shown) ->
"We're searching for your new PC." -> pairing-code screen, then a publish loop that
re-reads and re-publishes the on-screen code (rotates every ~59s) to the Coordination
Service until Target pairs.

| Dialog / condition | Heading / text | Where checked | Scope | Outcome |
|---|---|---|---|---|
| "Welcome to Dell Migrate." (re-appearing) | same | Both the discovery-wait loop and the publish loop (the one-off check at the very start of `run()` is separate and unchanged) | **Deadline-extending** | Non-fatal -- clicks "Let's get started" |
| "Do you trust the &lt;network&gt; network?" | contains "Do you trust the" | Both loops (not reliably confined to right after "Let's get started" -- confirmed to also appear well into the publish loop) | Plain `continue`, not deadline-extending | Non-fatal -- clicks Yes, continue |
| "This PC isn't connected to a network." | same | Both loops | Plain `continue`, not deadline-extending | Non-fatal -- `click_check_again()` |
| "Your battery is critically low." | same | Both loops, via shared `check_battery_critically_low()` | **Deadline-extending** (confirmed: expected to repeat indefinitely until the user actually plugs in a charger -- without this extension, 2-3 cycles alone used to exhaust the real timeout) | Non-fatal -- clicks Cancel (after its own delay), then immediately dismisses the follow-up "Are you sure you want to cancel?" confirm dialog via "No, don't cancel" |
| "The other PC isn't connected to a network." | same | Both loops, via shared `check_other_pc_disconnected()` | **Deadline-extending** | Non-fatal on Source (unlike Target's mirror-image dialog, which is terminal there) -- clicks "Cancel transfer", loop continues |
| "Your regional settings aren't supported." | contains "Your regional settings" (apostrophe-mismatch-safe substring match) | Both loops, via shared `raise_if_regional_settings_not_supported()` | N/A -- raises immediately once confirmed | **Fatal** -- clicking Close actually closes the whole app; raises `RuntimeError` |

### `SourceTransferFlow` (`flows/source/transfer_flow.py`)

Covers: "We've successfully linked your PCs." (brief, optional) -> "Are you ready to
start your migration?" -> "We're migrating your data now." -> one of three final
screens.

| Dialog / condition | Heading / text | Where checked | Scope | Outcome |
|---|---|---|---|---|
| "Welcome to Dell Migrate." (re-appearing) | same | `_poll_until_showing()` (covers linked-success/ready-to-migrate/migrating-data) and the final-screen loop | **Deadline-extending** | Non-fatal -- clicks "Let's get started" |
| "The other PC isn't connected to a network." | same | Same two loops | **Deadline-extending** | Non-fatal -- clicks "Cancel transfer" |
| "Your battery is critically low." | same | Same two loops | **Deadline-extending** | Non-fatal -- same Cancel + "No, don't cancel" sequence as the pairing flow |
| "Your regional settings aren't supported." | same | Same two loops | N/A -- raises immediately | **Fatal** -- same as the pairing flow |
| "We ran into a problem during your migration." | same | The final-screen loop only | Not deadline-extending (expected to resolve via retry, not linger) | Non-fatal -- clicks "Try Again", migration restarts and will land on a real final screen (or this again) |
| "We've completed your migration." (full success) | same | Final-screen loop | `summary_timeout`, then raise if none of the three final screens ever appears | Terminal success -- clicks Close |
| "Your migration is now complete." (partial, variant 1) | same | Final-screen loop | Same | Terminal partial -- dismissed via its own close **icon** (no Close button on this variant) |
| "Your migration summary is ready." (partial, variant 2) | same | Final-screen loop | Same | Terminal partial -- dismissed via `click_close_after_delay()` (deliberate pause before dismissing, giving the user a chance to read the summary) |

Both of Source's "partial migration" screens are legitimate, independently-confirmed
outcomes (this project was bitten twice by assuming only one of the two was ever real)
-- both are raced as alternatives, not one bet on over the other.

## Cross-cutting notes

- **Fatal dialogs never retry locally.** Every fatal dialog in this document ends the
  whole run via a raised exception, cleaned up by the caller's `Session.close()`
  (`orchestration/role_runner.py`'s `finally` block) -- app, browser, and WinAppDriver
  all torn down together, per explicit user direction ("if a single step fails then
  everything must be closed").
- **Non-fatal dialogs never count attempts.** None of the click-through dialogs in this
  project track "how many times has this happened" -- they rely entirely on the
  surrounding loop's own timeout (plain or deadline-extending) to eventually give up if
  something is genuinely stuck, rather than an arbitrary retry-count cap.
- **Defensively-added, not-yet-confirmed checks exist on purpose.** Several entries
  above (e.g. regional-settings/other-PC-disconnected in `TargetPairingFlow`) are
  marked "not yet confirmed to occur at this stage" -- they were added because the
  check is cheap (a single `is_showing(timeout=0.1)` per loop cycle) and the dialog was
  confirmed to occur at an *adjacent* stage, not because it was observed there directly.
  Treat these as insurance, not as proof the dialog has been seen at that exact point.
- **Known gaps**: email/password browser-sign-in steps are locator-only (inferred from
  a reference screenshot, never exercised live -- the test profile has consistently had
  a cached session). The PDF-migration-report validator (`validation/`, see
  [README.md](README.md#pdf-migration-report-validation)) is a separate, standalone tool
  and shares none of this dialog-handling machinery -- it runs after a migration
  completes, reading files/registry, not driving the UI at all.
